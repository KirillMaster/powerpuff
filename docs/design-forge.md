## Варианты
| | A. plain+ | B. forge (выбран) | C. Ralph-loop |
|---|---|---|---|
| Суть | Один Opus делает всё, плюс аудит спеки и финальный верификатор | Opus: аудит спеки → план → диспетчер → приёмка. Sonnet: приёмочные тесты, реализация. Haiku: прогоны гейтов, механические правки | Внешний цикл: свежий `claude -p` (Sonnet) на каждую задачу из `tasks.yaml`, файл прогресса; Opus только в начале и в конце |
| Opus-токены | 100% | ~20–35% (аудит, обзоры, приёмка) | ~10% |
| Риск | нарушает ограничение «Opus только оркеструет» | потеря контекста на передаче Opus→Sonnet | каждая сессия заново читает репо; цена контекста ×N; слабая согласованность архитектуры |
| Доказательства | plain уже ≈1.0 | Aider architect/editor +2–5 п.; Sonnet ≈ Opus на калибровке | только анекдоты (survey) |

**Выбор: B.** Это единственный вариант, где выполняются все ограничения цели (Opus только оркестрирует и проверяет, исполняют дешёвые модели), и при этом у каждой части есть хоть какие-то данные. От C берём внешний драйвер с файлом состояния, чтобы продолжать после rate limit. A — запасной вывод «plain плюс X», если B проиграет.

## Ответы на 6 обязательных вопросов
1. **Неоднозначности до кода.** Шаг `audit` (Opus, один проход, только чтение) читает спеку и нужные места кода и пишет `.forge/decisions.md`. В нём каждое место, которое допускает два прочтения, выбранное прочтение и основание. Правило выбора — по порядку: существующий код, тесты и конвенции; буквальный текст спеки; согласованность с другими пунктами; более строгая или безопасная трактовка. Если оба прочтения совместимы, реализуем оба (например, принимаем обе формы ввода). Ночной прогон не останавливается никогда. Есть отдельный режим `/forge --preflight` для запуска при человеке: он делает только аудит и задаёт блокирующие вопросы одним списком; ответы записываются в `decisions.md` как `D<n> (human)`. Ночной прогон берёт этот файл как готовый.
2. **Исполняемая спека.** Шаг `acceptance`: отдельный субагент Sonnet пишет приёмочные тесты через публичный интерфейс (HTTP/CLI/API). Каждый тест помечен `R<n>` и ссылается на пункт спеки или `D<n>`. Субагент не видит плана реализации. Opus проверяет покрытие: каждый `R` покрыт хотя бы одним тестом. После этого тесты замораживаются: `sha256` записывается в `.forge/frozen.sha256`, гейт `frozen` сверяет суммы после каждой задачи. Исполнитель тесты не трогает. Если тест противоречит спеке, исполнитель пишет `dispute` в state, и спор решает Opus на приёмке; только он может разморозить тест с записью в отчёт. Скрытого набора в продакшн-режиме нет (его роль играет бенч). Защиту дают заморозка и отдельный автор тестов.
3. **Разделение моделей.** Opus (главный поток) делает аудит, план (группы `T<n>` по `tasks.yaml` или по спеке), брифы, разбор провалов и решение «повторить, эскалировать или принять». Sonnet: приёмочные тесты; реализация каждой группы (один исполнитель за раз, свежий субагент на группу с брифом: цель, `R`-идентификаторы, файлы из дайджеста, конвенции, команды гейтов); исправления после приёмки. Haiku: дайджест репо (`.forge/digest.md`, путь:строка, один раз), прогоны гейтов и формат/линт-фиксы. Opus не перечитывает репо: работает по дайджесту, по кратким JSON-отчётам исполнителей и по `git diff --stat`. Эскалация: если Sonnet дважды провалил одну группу, Opus делает третью попытку сам, в своём контексте, с полным логом провала.
4. **Цикл качества.** После каждой группы механические гейты (format, lint, architecture, tests, frozen). Их запускает сам исполнитель, а для гейтов из `bob-pipeline.yaml` — `scripts/ci_gates.py`. Мутационное тестирование — только если инструмент уже есть в конфиге проекта (`tools[]` категории mutation), детерминированно, на изменённых файлах, без LLM-роли: доказательств эффекта на скрытые тесты нет (survey). Независимая приёмка одна, в конце: субагент Opus со свежим контекстом и только чтением сверяет спеку, `decisions.md`, diff и результаты тестов и ищет только пробелы корректности (стиль пропускает). Затем не больше 2 раундов исправлений силами Sonnet. Проверок на каждую задачу нет: Anthropic их убрал, а в пилоте они стоили ×10.
5. **Долгий прогон.** Состояние хранится в `.forge/state.json`: фаза, задачи со статусами, попытки, споры, бюджет. `/forge` всегда идемпотентен: читает state и продолжает с первой незавершённой задачи. Каждая группа заканчивается коммитом. Драйвер `scripts/forge_run.py` запускает `claude -p "/bob-pipeline:forge …"` в цикле: при rate limit спит до времени сброса (парсит сообщение; иначе 15 мин), при обрыве делает `--resume` или новую сессию с тем же state; останавливается по маркеру `FORGE: done|failed`, по `--max-hours` или `--max-usd` (сумма `total_cost_usd`). Прогресс видно в `.forge/progress.md`, одна строка на событие.
6. **Итог.** `.forge/REPORT.md` не длиннее одного экрана: статус; таблица `R → тест → pass`; гейты (последний прогон); решения `D<n>` там, где спека молчала; споры и размороженные тесты; что под вопросом; стоимость по моделям. **Готово под ключ** = все `R` покрыты зелёными тестами, frozen-хэши целы, все гейты зелёные, у приёмки нет открытых пробелов → `FORGE: done`. Иначе `FORGE: failed` со списком того, что не закрыто.

## Что сознательно не делаем (и почему)
- Нет ролей architect, hardener и QA на каждый слайс: пилот показал ×10 к цене без прироста.
- Нет self-consistency (N образцов): у всех образцов одна и та же ошибка прочтения, а промахи у нас именно такие.
- Нет worktree на каждый слайс: исполнитель один и работает последовательно.

## Проверка
Вариант `forge` в `bench/bench.yaml`, сравнение по `bench/PROTOCOL-representative.md`. Гипотеза H-forge: forge ≥ plain по качеству (≥ +0.03 или равенство) при доле Opus ≤ 40% стоимости. Если качество равно, а цена выше, — итерация (не больше 3), затем вывод «plain плюс X».

## Ревизия после дополнительного исследования (2026-11-17)
Источники: `docs/research/harness-survey.md` §5, `docs/research/multi-agent-evidence.md`, `docs/research/hackathon-winner-ecc.md`.
- **Подтверждено:** один писатель; параллельно только read-only; тесты из спеки до кода и заморозка (тесты, написанные отдельно от кода, ловят 25% дефектов, после кода — 14%); одна свежая приёмка в конце; состояние на диске; лимит итераций.
- **Изменено:** вердикт `done` выносит скрипт `scripts/forge_check.py`, а не модель (как у Tekton: SHIP решает orchestrate.mjs по рубрике). Скрипт проверяет покрытие R тестами, зелёные приёмочные тесты, целые frozen-хэши и зелёные гейты. LLM-приёмка добавляет пробелы, но сама зелёный цвет не ставит.
- **Под вопросом:** разделение «Opus руководит, Sonnet пишет» по литературе не доказано (ManagerWorker 62 vs 60%, пара Aider 78.2 vs 88.0% у одиночной модели). Проверяем абляцией на бенче: `forge` (писатель Sonnet) против `forge-opus` (писатель Opus, остальное то же). Решает правило протокола.

| Показатель | forge v1 |
|---|---|
| Итог | `FORGE: done`, 59 тестов зелёные, хэши целы |
| Стоимость (условная) | $11.42: Opus 54%, Sonnet 46% |
| Откуда | Opus-оркестратор: 70 ходов по ~80 тыс. токенов контекста (5.7 млн токенов чтения кэша); Sonnet-рабочие: 94 хода, 6.3 млн |
| Вывод | цена заложена в архитектуру: модель-оркестратор платит за каждый ход всем своим контекстом, каждый новый рабочий заново читает репозиторий |

Изменения:
| Было (v1) | Стало (v2) | Основание |
|---|---|---|
| Оркестратор — сессия Opus (`commands/forge.md`) | Оркестратор — скрипт `scripts/forge_run.py`: состояние, порядок шагов, хэши, гейты, бюджет, ожидание лимита | детерминированная работа не требует модели; у Tekton решение тоже принимает скрипт |
| Haiku-дайджест + аудит + 3–8 рабочих по группам | 4 типа сессий: аудит (Opus), приёмочные тесты (писатель), сборка (писатель, один контекст, продолжается при красной проверке), приёмка (Opus, свежий контекст) | один писатель с непрерывным контекстом; репозиторий читается один раз |
| «Готово» объявляет модель после `forge_check` | `forge_check` вызывает скрипт; строку `FORGE: done` печатает скрипт | слово модели не считается |
| Изменённый замороженный тест чинит оркестратор | скрипт восстанавливает файл из git до запуска гейтов | детерминированно |
| Opus подхватывает работу сам | не более 3 кругов писателя, затем одна сессия сильной модели, затем `failed` с отчётом | ограниченная цена провала |

Критерий итерации: то же качество на той же спеке при стоимости заметно ниже v1; на бенче — не хуже plain по качеству. Если v2 не обгонит plain и по цене, честный вывод по правилу промпта: «лучший харнесс = plain плюс аудит неоднозначностей и замороженные приёмочные тесты».
